# LANDZO Locations

## Scope

Step 4 implements the backend Location Catalog only. It provides a canonical Sri Lankan hierarchy for future property creation, filtering, SEO routes, public search, enquiries, analytics, and admin cascading selectors.

Step 4 does not implement Property models, exact property pins, Leaflet UI, Explore Map, media, enquiries, blogs, CMS, or frontend work.

## Hierarchy

LANDZO V1 supports exactly four managed location levels:

```text
province
district
city
area
```

Valid parent relationships:

```text
province -> parent = null
district -> parent must be province
city     -> parent must be district
area     -> parent must be city
```

The backend rejects invalid structures with stable errors such as `INVALID_LOCATION_HIERARCHY` and `LOCATION_PARENT_NOT_FOUND`. The frontend cascading selector is a usability layer only; the backend remains authoritative.

## Model

Location fields:

```text
name
level
parent
canonicalKey
slug
status
sortOrder
createdBy
updatedBy
createdAt
updatedAt
```

`level` is immutable after creation. Renaming is allowed. Re-parenting is allowed only within the same level and only when the new parent has the required parent level.

`canonicalKey` and `slug` are generated by the server. Clients cannot submit or overwrite them through create/update APIs.

## Canonical Normalization

The canonical key normalizes common duplicate variants without trying to guess every possible spelling.

Normalization handles:

- capitalization
- leading/trailing spaces
- repeated spaces
- separators such as spaces, hyphens, slashes, underscores, commas, and periods
- numeric tokens with unnecessary leading zeroes

Examples that resolve to the same canonical identity:

```text
Colombo 3
Colombo 03
Colombo-03
colombo 03
```

Canonical key:

```text
colombo 3
```

Slug:

```text
colombo-3
```

## Duplicate Prevention

Duplicates are blocked under the same hierarchy parent using:

```text
level + parent + canonicalKey
```

Duplicate attempts return:

```text
409 LOCATION_ALREADY_EXISTS
```

Raw MongoDB duplicate-index details are not exposed through the API.

## Status Behavior

Supported statuses:

```text
active
inactive
```

Inactive locations remain historically identifiable and can still be retrieved through management APIs. They should not normally be offered for new property selection.

The backend prevents creating an active child under an inactive parent with `LOCATION_PARENT_INACTIVE`.

The backend prevents deactivating a parent that still has active children with `LOCATION_HAS_ACTIVE_CHILDREN`.

There is intentionally no DELETE endpoint in Step 4. Location removal semantics should be revisited only after future property references exist.

## APIs

All routes are admin/staff routes under `/api/v1/admin/locations`.

Read routes require `location.view`:

```text
GET /api/v1/admin/locations
GET /api/v1/admin/locations/:locationId
```

Management routes require `location.manage`:

```text
POST  /api/v1/admin/locations
PATCH /api/v1/admin/locations/:locationId
PATCH /api/v1/admin/locations/:locationId/status
```

No delete route is implemented.

List filters:

```text
page
limit
level
parentId
status
search
```

The list endpoint is paginated with a bounded maximum limit and supports parent-based lookups for future cascading selectors.

## Response DTO

Location APIs return explicit safe DTOs, not raw Mongoose documents.

Safe shape:

```json
{
  "id": "...",
  "name": "Colombo",
  "level": "district",
  "slug": "colombo",
  "status": "active",
  "sortOrder": 10,
  "parent": {
    "id": "...",
    "name": "Western Province",
    "level": "province",
    "slug": "western-province"
  },
  "createdAt": "...",
  "updatedAt": "..."
}
```

The DTO does not expose `canonicalKey`, `createdBy`, `updatedBy`, `__v`, or Mongo internals.

## Catalog vs Property Coordinates

The Location Catalog is a reusable administrative hierarchy. It does not store exact map pins.

Exact property location is deferred to the future Property module and will use a GeoJSON Point such as:

```json
{
  "type": "Point",
  "coordinates": [79.8612, 6.9271]
}
```

Required future coordinate order:

```text
[longitude, latitude]
```

Leaflet map search, pin placement, and coordinate capture are future Admin Property Wizard work. Step 4 does not add fake coordinates to catalog records.

## RBAC

Step 4 adds:

```text
location.view
location.manage
```

Owner resolves all registered permissions automatically. Fresh Admin role bootstrap includes location view/manage because Admin performs operational property management.

Existing non-owner customized permissions are preserved during bootstrap. Adding the new permissions does not overwrite a configured Admin permission array.
